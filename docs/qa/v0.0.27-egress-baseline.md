Captured: 2026-07-30 (Africa/Cairo)
Supabase project: `iejbogkqknldxoyepvun`

## Method

The baseline combines:

- `supabase inspect db calls --linked`
- `supabase inspect db outliers --linked`
- `supabase inspect db traffic-profile --linked`
- `supabase inspect db index-stats --linked`
- `supabase inspect db bloat --linked`
- the affected Android account database and its durable outbox
- TaskMaster Pro's in-process request, payload, Realtime-message, and repeated-query counters

`pg_stat_statements` values below cover the current PostgreSQL statistics
window. They are not presented as a single 15-minute scenario. Post-repair
acceptance uses deltas from this captured baseline plus the bounded client
scenarios listed at the end of this document.

## Index Advisor equivalent and relation health

The linked project's index statistics confirmed that the hot paths already use
the intended indexes:

- `processed_commands_user_id_command_id_key`: 6,817 scans, 100% index use
- `sync_change_log_pull_idx`: 9,503 scans, 100% index use
- `sync_change_log_change_sequence_key`: 36,462 scans, 100% index use
- `activity_segments_user_id_id_key`: 18,353 scans, 100% index use
- `roadmap_task_links_identity_idx`: 101,013 scans, 100% index use

The bloat report found only small absolute waste (largest single item: 160 kB
for `task_resources`). Adding more indexes would increase write amplification
without fixing the repeated-call source. The release therefore focuses on
command convergence, one account channel, compact change cursors, and
eliminating repeated row fetches.

## Pre-reset recovery point

Before the authorized operational-data reset, TaskMaster Pro exported 13,418
owner-scoped rows from 75 public tables to:

`tool/backups/v0.0.27-pre-reset-20260730/owner-public-data.json`

The reset preserved the authenticated account, profile, user settings, task
domains, and encrypted vault while removing obsolete tasks, roadmaps,
Activity, health, device, processed-command, change-log, and conflict rows.

## Exact affected-device queue evidence

The Android account database contained:

- 44 rejected atomic Activity classifications before the transport repair.
- legacy readable segment identities such as
  `android-history-com.android.launcher-...` in UUID-typed server operations.
- repeated replacement classifications whose source segment could never be
  accepted.
- a same-ID starter Task-domain create reported as a revision mismatch.

This established the loop:

```text
malformed legacy Activity identity
→ permanent server rejection
→ replacement command
→ point-read recovery
→ another rejected classification
→ repeated change-log and Realtime traffic
```

## Repeatable acceptance scenarios

For each scenario, record request count, rows, downloaded/uploaded bytes,
Realtime messages, active channels, duplicate handlers, repeated query
fingerprints, failed commands, and authoritative snapshots:

| Scenario | Duration |
|---|---:|
| App idle | 15 minutes |
| Dashboard open | 15 minutes |
| Unchanged running timer | 30 minutes |
| Activity capture | 30 minutes |
| Pause/resume across two phones | one transition sequence |
| Reconnect | one network cycle |
| Report opening | one cold and one warm open |
| Task application linking | one normal and one simultaneous link |

Required unchanged-state result:

- no timer-second writes, reads, or broadcasts
- no repeated full-account pull
- no raw foreground-observation uploads
- one account channel and one event handler
- no duplicate logical command IDs
- no retry of permanently invalid transport commands
